Case 01 · Executive sensing

Acquisition War Room

The recurring question was simple: what changed, why, and where should the operating team focus next? The hard part was producing one briefing that combined quantitative movement, business context, operating signals, and an honest verification state.

01Parallel specialists, narrow jobs. Headline metrics, deeper funnel analysis, segment movement, operating signals, and business context ran as separate workstreams.
02Analyzed summaries, not raw-table handoffs. Each specialist returned a compact result so synthesis did not repeat the analysis or ingest every row.
03Verification stayed visible. An unverified or review-required result could still be useful, but nobody could mistake it for an approved answer.
04The decision sat next to the evidence. The number, decomposition, caveat, next investigation, and authority boundary lived on the same screen.

Case 02 · Investigation + action

Abandonment Intelligence

The War Room says what moved. Abandonment Intelligence goes underneath it and asks what specific rule, route, or product flow deserves investigation. It rejects “conversion is down” as an answer because a rate alone does not tell an engineer or operator what to do.

01Investigators followed funnel breakpoints. Each agent owned a narrow abandonment area instead of letting one generalist scan the entire business.
02Every finding needed a shape. Affected population, broken flow, durability, evidence, owner, next action, and confidence.
03Known-good behavior was encoded. The system had to distinguish a real defect from an intentional rule or expected operating pattern.
04Synthesis ranked work, not observations. The result was a reviewable action list with gates, not a longer dashboard.

Choose the work

Start with a decision that repeats. Skip the chatbot that answers anything.

A production agent earns its maintenance cost when the work recurs, the path can become reliable, the answer changes something, and the downside is understood.

Four questions decide whether to build.

The first three come from the build-first lesson. The fourth prevents a high-impact use case from quietly crossing a line the team has not designed for.

  • 01Frequency: How often does this exact work return?
  • 02Repeatability: With the same inputs, do the metric, direction, drivers, caveat, and basic recommendation stay stable?
  • 03Decision value: Who changes what because this answer exists?
  • 04Decision risk: What is the cost of a quietly wrong answer or an action taken too early?

Define the job

Write the decision contract before you design the agent.

The contract forces one useful sentence: who needs what answer to make which decision, with what authority and human boundary.

A useful agent has a narrow job and an explicit line it cannot cross.

Do not start with the tools. Start with the decision. Then specify the inputs, output, authority, and review trigger. The contract should fit on one screen and be readable by the business owner, data owner, and builder.

AI Analyst preflight: Goal → Decision → Metric → Hypothesis. If you cannot state all four, ask before touching the data. Add a concrete success condition so the analysis has a finish line.

Say this

“The agent does the repeatable analytical work. The person still owns what matters, reviews the result, and makes the final call.”

01User + forumWho receives this and where?
02Decision + actionWhat choice and next move can change?
03OutputWhat must the agent return?
04EvidenceWhat must be true before it answers?
05AuthorityWhat may it do on its own?
06Stop conditionWhen must it clarify, review, or refuse?
07Human ownerWho owns the final decision and repair?
Map the production path: where does each guarantee live?

A prompt in Codex, Cursor, or Claude can remind the agent what to do. Shared guarantees belong in the common path the clients call. Label who owns permissions, versions, persistence, failure handling, and review.

01HarnessCollects intent and shows the result. It should not be the only enforcement point.
02Tool / MCP contractValidates inputs, scope, versions, and allowed operations.
03Approved contextSupplies the metric, source precedence, caveats, owners, and expiry.
04Scoped source adapterUses read-only credentials, allowlists, limits, and timeouts.
05ValidationRuns source, structure, logic, business-rule, and reconciliation checks.
06Proof storeSaves the question, versions, source result, checks, caveats, and outcome.
07Human reviewOwns high-risk, conflicting, novel, or failed paths.
08Correction + eval memoryTurns reviewed failures into shared fixes and regression cases.
For [user / decision forum], this agent answers [recurring question] so they can decide [specific action].

It may: [read / calculate / compare / draft / recommend].
It may not: [publish / spend / change source truth / take irreversible action].

It must return: what it did next, the answer or clarification, source, freshness, calculation path, assumptions, caveats, validation, and next action.

It may answer only when: [required evidence and validation].
It must clarify, review, or refuse when: [risk, novelty, conflicting evidence, missing owner, failed validation, or action threshold].
Human owner: [role accountable for the decision and repair].

Bind the meaning

Give the agent the context your team normally carries in its head.

Trust starts upstream: one definition, named owners, an approved source path, freshness, caveats, and precedence when sources disagree.

The goal is not “more context.” It is the smallest approved context that changes the path safely.

For each golden question, distinguish what must exist, what was available, what the agent retrieved, and what actually changed the answer. This makes a miss diagnosable instead of producing another document dump.

  • 01Metric: definition, formula, grain, time zone, filters, exclusions, owner.
  • 02Source: approved dashboard, query, semantic object, or table; freshness and lineage.
  • 03Business: product changes, promotions, seasonality, operating rules, decision thresholds.
  • 04Memory: known caveats, corrections, prior reviewed answer paths, expiry rule.
Source conflict rule

If two approved artifacts disagree and no precedence rule exists, choose Review or Refuse. Do not pick the newest-looking number.

Eligible contextApproved material available to the agentOwned + current
Retrieved contextWhat the agent actually pulledObserved at runtime
Applied contextWhat changed the path, result, caveat, or outcomeEvidence of use

Prove the answer

A safe system knows when to answer, ask, send to review, or stop.

Choose what the agent should do before polishing the prose. A fluent answer never gets priority over the correct outcome.

Answer

The approved path ran and the required validation passed. Return the answer with evidence and caveats.

All checks pass
Clarify

The question is missing the smallest detail needed to choose the metric, period, segment, grain, or comparison.

Missing scope
Review

The path is plausible, but ownership, business context, a novel join, benchmark, or decision risk needs a person.

Plausible, not proven
Refuse

The source is unsafe, stale, contradictory, out of scope, restricted, or failed a blocking validation check.

Blocking check failed

Run checks in dependency order: source tie-out and structure first, then logic, business rules, and statistical or segment-reversal checks. A failed source tie-out stops the analysis; more sophisticated validation cannot repair the wrong input.

Operate it

Production begins when the demo ends.

A production plan needs owners, a review rhythm, monitoring, correction memory, cost, and a clear rule for stopping or narrowing the system.

Assign five owners. One person can wear several hats.

  • 01Decision owner: owns the business action and risk.
  • 02Metric owner: approves the meaning, caveat, and review date.
  • 03Data owner: owns source quality, freshness, and change notices.
  • 04System owner: owns the path, tests, cost, permissions, and incidents.
  • 05Reviewer/operator: samples live answers and turns corrections into durable fixes.
Measure the system

Start with four questions: Did it save time? Was the answer good? Did the decision improve? Was the team experience better? Track quietly wrong results, false blocks, stability, review burden, and cost beside them.

01 · Data + permission

Least access wins

Classify allowed and prohibited data. Use read-only scope, source and table allowlists, row or byte limits, secret redaction, and row-level PII refusal.

02 · Runtime behavior

Fail predictably

Set timeout, retry and backoff, idempotency, rate and concurrency limits, degraded-result rule, cached fallback, and circuit breaker.

03 · Version + release

Know what changed

Pin the route, context, metric, model, and threshold versions. Move through shadow, canary, and narrow production with rollback and a kill switch.

04 · Observability

Trace every serious claim

Log source snapshot, freshness, response outcome, validation stages, latency, tokens, cost, calls, fallback, reviewer label, and correction id.

05 · Audit + incident

Review the right risk

Sample routine answers; review every finance, board, customer, or high-impact answer. Preserve evidence, pause the affected route, repair, regress, and name who may resume.

06 · Value + capacity

Earn the next use case

Compare with the manual baseline. Track adoption, reuse, time saved, review burden, cost per run and month, and whether the decision or team experience improved.

Live-session notes

How this workshop stays useful when a demo fails.

These notes are here for anyone running the session again. The learning depends on the path and judgment, not a lucky API response.

Expand live-session preparation, room rules, and scripts

30 minutes before

  • Open this page and export a blank starter pack.
  • Download the lab zip and run python3 verify.py.
  • Check any MCP or warehouse route you plan to demo; do not make it the critical path.
  • Silence notifications and share one browser window.
  • Put the three Q&A windows and two breaks in your calendar.

Room contract

  • Use sanitized company examples only.
  • No credentials, proprietary SQL, raw customer records, or restricted files.
  • No coding experience is required; the harness can write and run the files.
  • Questions about a specific company stay at the design level.
  • If a source cannot run, state that clearly and use the lab kit.

Energy design

  • Use chat in the first two minutes.
  • Do not talk for more than ten minutes without a room action.
  • Ask students to predict an outcome before revealing it.
  • Use the synthetic case whenever an example is sensitive.
  • Timebox feedback to the current artifact.

If the live agent fails, teach the failure.

Show the planned path, state that the source did not run, and ask what the agent should do next. Use the lab’s proof as the completed example. A failed call becomes a production lesson, not dead air.

Opening: “By 2 PM, you will have one written production plan. We are going to build it in six pieces, and you will use the same real question all day.”
Closing: “Do not start Monday by building the whole agent. Start by locking one question, one owner, and one approved metric path. Then make one failure visible and fix it.”
